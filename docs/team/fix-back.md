## 1. 根因:一个变量承担了两种语义

改前导航是 `val stack = remember { mutableStateListOf<Int>() }`,`current = stack.lastOrNull()`。
**同一个 `stack` 同时被读出两种含义**,而且两者都是 `Int`,编译器不会给任何提示:

| 读法 | 含义 | 正确用法 |
|---|---|---|
| `stack.lastOrNull()` | **节号**(0..10) | 顶栏节号、内容分发、下一节目标 |
| `stack.lastIndex` / `stack.size` | **栈深度**(走过/压过几层) | 「返回上一级」弹一层 |

两者的关系是**巧合**而非恒等:只有「从第一节一路顺序点下来」时 `lastIndex == 节号`。
一旦从目录或首页直达,两者立刻分叉。

**这一轮(返回语义)的 bug 就是这个分叉的直接产物**:

```kotlin
fun stepBack() { if (stack.size > 1) stack.removeAt(stack.lastIndex) else home() }
```

* `stack.size > 1`(栈深度 ≥ 2)→ 弹一层 → **回到上一节**;
* `stack.size == 1`(栈深度 1,即从首页/目录直达)→ `home()` → 回首页。

于是同一个「点左上角返回」的动作,产生了两种结果 —— 取决于用户是"顺着点下来"还是"直接跳进来"。
用户反馈的正是这个不一致。

> 上一轮(`docs/team/nav-section-index.md`)修的是同一根源的另外三个症状(顶栏「第 1/11 节」、
> 末节漏出「下一节」、末节点「下一节」跳回第一节)。那次的修法是**加约定 + 加注释**:
> 明确写「`stack.lastIndex` 是栈深度,永远不要用它算节号」,并把误用处逐个改成节号。
> 注释挡不住第二次 —— 半年后新增一个返回入口,谁还记得栈深度那套约定。
> **如果一个 bug 的根因是"两个量可能不一致",正确修法是减少到一个,而不是加注释区分。**

## 2. 改动

```kotlin
// 改前
val stack = remember { mutableStateListOf<Int>() }
val current = stack.lastOrNull()
fun go(i: Int) { if (i != current) stack.add(i) }
fun home() { stack.clear() }
fun stepBack() { if (stack.size > 1) stack.removeAt(stack.lastIndex) else home() }
BackHandler(enabled = stack.isNotEmpty()) { stepBack() }

// 改后
var current by rememberSaveable { mutableStateOf(-1) }   // -1 = 首页
val inSection = current >= 0
fun go(i: Int) { current = i }
fun home() { current = -1 }
BackHandler(enabled = inSection) { home() }
```

| 入口 | 改前 | 改后 |
|---|---|---|
| 顶栏 `←` | `stepBack()`(按栈深度弹层) | `home()`,一律回首页 |
| 系统返回手势/键 | `enabled = stack.isNotEmpty()` → `stepBack()` | `enabled = current >= 0` → `home()`;在首页时 `enabled = false` 交还系统退出 |
| 底栏「← 上一节」 | `stepBack()`(弹一层) | `current - 1`,下限 0;`current == 0` 时 `= -1` 回首页,**不禁用** |
| 底栏「下一节 →」 | `stack.add(current + 1)`,越界 `home()` | `current + 1`,末节兜底 `-1` |
| 底栏「回到首页」(末节) | `stack.clear()` | `home()` |
| 目录选中第 i 节 | `go(i)` → `stack.add(i)` | `current = i` |
| 首页主按钮/列表项 | `go(i)` → `stack.add(i)` | `current = i` |
| 顶栏节号 | `current + 1`(上一轮已修对) | 不变 |
| 顶栏进度条 | `current / (total - 1f)`(上一轮已修对) | 不变,仍只在 `inSection` 时渲染 |
| `SectionPicker` 形参 | `current: Int?` | `current: Int`(该 sheet 只在节内可达) |

**状态唯一性**:`current` 是唯一的导航状态,`inSection = current >= 0` 是它派生的显示开关。
顶栏/底栏/内容分发/ScreenBody 的 `when` 全部读同一个 `current`,不再存在"读栈顶还是读栈深度"的选择。

**`rememberSaveable` 而非 `remember`**:进程内旋转/重建(配置变更)不丢当前节,
`MutableState<Int>` 可被 `SaveableStateRegistry` 直接存取。

**未改动**:`Charts.kt` / `Experiments*.kt` / `Components.kt` / `Home()` / `SectionFooter` 与
`SectionPicker` 的视觉与布局、`SectionFooter` 的 `last` 不等式判定、`SectionPicker` 的
`on = current == i` 高亮逻辑、首页滚动与主按钮。未新增依赖。

## 6. 为什么去掉栈能**根除**这一类 bug

### 6.1 把"选错来源"变成"没有第二个来源"

改前,"我在哪一节"没有直接可读的量,必须从 `stack` 推导;而 `stack` 至少暴露了两种读法
(`lastOrNull()` = 节号、`lastIndex`/`size` = 深度),**类型全都是 `Int`**,读错不会编译失败、
不会 lint 报警、运行时也只是显示错一个数字。这类 bug 的特征就是"静默":上一轮 3 个症状、
这一轮 1 个症状,全部是静默的。

改后,"我在哪一节"就是 `current` 这一个 `Int`。任何读取点读到的都是同一个值,
**"读错来源"这个动作在结构上不再存在**。没有第二种读法,就不可能读错。

### 6.2 上一轮修的是症状,这一轮修的是结构

上一轮的修法可以概括为"加约定 + 加注释 + 逐点替换":

```kotlin
// 节号 = current(栈顶存的节号),不是 stack.lastIndex(栈深度)。
// 从目录直达第 11 节时栈是 [10],lastIndex=0 会误报「第 1 / 11 节」。
```

注释能提醒**读过这段代码的人**,但挡不住**新写的返回入口**。这一轮的 bug 恰恰诞生在
上一轮刚改过的同一个函数 `stepBack()` 附近 —— 上轮刚给它写了一大段注释解释"这是故意用栈深度语义的",
上轮结尾还专门写了「建议手测路径 7: 任意节连按系统返回」,结果返回语义本身就是错的。
**靠注释维持的约定,在同一份文件里第二次被违反。**

> 判据:当一类 bug 的根因是"两个量可能不一致"时,加注释区分只是把编译期能发现的问题
> 推迟到 review 期;**减少到一个量**才是把问题从"不许犯"变成"犯不了"。

### 6.3 顺带消掉的三个结构性问题

1. **无界增长**:改前每点一次「下一节」/ 目录跳转都 `add` 一次,栈深只增不减,长会话下
   `SnapshotStateList` 一直变长;改后是定长的单个 `Int`。
2. **多余防御层**:改前为了压住"状态可能非法",叠了 `last` 不等式 + `onNext` 内部兜底 +
   `entries.getOrNull(current)?.title ?: ""` 三层防御。改后 `current` 恒在 `-1..10`,
   越界在结构上不可达(防御保留,无害,但不再是必需品)。
3. **历史路径泄漏到当前状态**:改前 `stepBack()` 的结果取决于用户"之前走过的路",
   也就是当前界面被一段**用户已经离开的历史**决定。改后界面状态只由当前值决定,
   可预测性显著提高 —— 这正是用户在反馈里说的"不符合正常逻辑"。

### 6.4 职责划分(改后)

| 意图 | 唯一入口 |
|---|---|
| 节内前后移动 | 底栏「上一节 / 下一节」 |
| 离开详情层 | 顶栏 `←`、系统返回、末节「回到首页」、目录里的「回到首页」 |
| 跳到任意一节 | 目录 |
| 进入应用 | 首页「从第一节开始」/ 列表项 |

"详情页的返回"只有一种含义(回首页),所以它没有分支,也就没有行为不一致的可能。
