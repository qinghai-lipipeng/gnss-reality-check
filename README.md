# 1 微秒 · 定位精度的真相

一个纯离线、零权限的安卓科普 App。它不讲 GPS 怎么定位,而是讲一件容易被搞混的事:

> **定位精度由"量"的品质决定,不由各家星座的"不同算法"决定。**

11 个小节,每节都有可交互的实验,目标是让用户**亲手把结论做出来**,而不是被告知结论。

---

## 核心结论(以及它的准确版本)

常见的说法是"定位精度取决于授时精度"。这个说法方向对,但不够准确。真正的机制是:

> **解算器只吃"差异",不吃"共模"。**

接收机钟差是 c·δt_r,本来就是最小二乘的四个未知量之一。所有伪距一起偏一个相同的量,
这个共模偏移会被**完整吸收**,位置几乎不动。实测:给接收机加 1 微秒恒定钟差,位置只差零点几米。

能真正打进位置的是**各颗星之间对不齐**的部分:

| 对照项 | 实测结果 |
|---|---|
| GPS / 北斗 / 伽利略 / 格洛纳斯 / 四系统全开,误差差 | **0.20 m** |
| 换更高级的解算算法(OLS/WLS/EKF/粒子滤波),终值差 | **< 0.4 m** |
| 卫星间钟差 ±20 ns(等效 6 m) | **+4.8 m** |
| 不做相对论偏心修正 | **+2 m** |
| 多路径(城市) | **5~15 m** |

所以准确的说法是:**时间基准的彼此一致,比某个钟的绝对快慢重要得多。**

同一条规律还解释了另外两件事:
- **电离层**:共模延迟被钟差吸收,真正打位置的是水平梯度
- **多路径**:各星独立的那部分会被平均掉,**同一片楼宇对同方位角卫星的反射是共模的**,不会平均掉 —— 这才是城市误差降不下来的原因

## 特性

- **纯离线**:不联网、不申请任何权限
- **真解算器**:不是把图贴出来让你看。内置四星座轨道模型、Klobuchar 电离层、
  Saastamoinen 对流层、相对论偏心修正,跑真实的加权最小二乘
- **四星座对比**:GPS / 北斗(含 MEO+IGSO+GEO)/ 伽利略 / 格洛纳斯,按各自 ICD 的轨道设计参数
- **四种滤波器**:普通最小二乘、加权最小二乘、扩展卡尔曼、粒子滤波,同场对比
- **混合定位**:WiFi 指纹 / 基站 / 道路匹配 / 惯导,看"卫星量不到的时候怎么办"
- **三层深度**:同一件事讲三遍 —— 人话(零公式)/ 机理(带数量级)/ 推导(公式与 ICD 出处)
- **术语开关**:默认说人话,一键切专业术语
- **自绘图表**:天空图、收敛曲线、误差预算瀑布、钟差尺,全部 Canvas 手绘,无图表库依赖

## 编译

需要 JDK 17、Android SDK(compileSdk 35 / build-tools 35)。

```bash
cp local.properties.example local.properties
# 改成你自己的 SDK 路径:sdk.dir=/path/to/android-sdk

./gradlew testDebugUnitTest    # 40 个物理与逻辑测试
./gradlew assembleDebug       # 产物:app/build/outputs/apk/debug/app-debug.apk
```

依赖仓库已配好国内镜像(阿里云 + 腾讯云)。Gradle 8.11.1 / AGP 8.7.2 / Kotlin 2.0.21。

> `gradle.properties` 里的 `org.gradle.jvmargs=-Xmx1100m` 是按 3 GB 小机器调的,
> 内存宽裕可以调大并打开 `org.gradle.parallel`。

```
app/src/main/java/com/oneus/lab/
├─ sim/          轨道与观测生成
│   ├─ Vec3.kt            向量 + WGS-84 地理坐标
│   ├─ Constellation.kt   四星座轨道设计参数 + Keplerian 传播
│   ├─ Atmosphere.kt      Klobuchar 电离层 / Saastamoinen 对流层
│   ├─ Scenario.kt        场景、误差预算、双频伪距生成
│   └─ LabEngine.kt       实验引擎(各实验的数据出口)
├─ solve/        解算
│   ├─ LinAlg.kt          小矩阵求逆与解方程
│   ├─ IonoCorrector.kt   四种电离层处理 + 相对论/对流层改正
│   ├─ LsSolver.kt        线性化最小二乘 + DOP + 几何质量门限
│   └─ Filters.kt         OLS / WLS / EKF / 粒子滤波
├─ fusion/       混合定位(WiFi / 基站 / 道路匹配)
└─ ui/           Compose 界面
    ├─ AppRoot.kt         路由与导航意图(纯函数可测)
    ├─ theme/             M3 深色配色与排版
    ├─ charts/            自绘图表 + 通用组件
    └─ experiments/       11 个实验页,每页三层文案
        ├─ SectionEnv.kt  一节的全部环境(深度/术语/跳转),纯数据可测
        ├─ ExpShell.kt     实验页通用外壳 + 常驻区 + 结论条
        └─ Experiments1-3 11 个实验页,每页三层文案
```

### 一节只有一个环境对象

11 个实验页以前各接一遍 `depth` / `onDepth` / `onGo` 这类**平行参数**,
每加一个跨节能力就要改 11 处签名。这直接导致「术语:人话/专业」开关**点了没反应** ——
`AppRoot` 拥有 `tech`、首页也画了开关,但 `ScreenBody` 没有任何参数能把它递下去,
于是 `term()` 全项目 **1 处定义、0 处调用**:控件承诺了一个它够不到的能力。

现在这些收进 `SectionEnv` 一个对象,由 `AppRoot` 构造一次往下传。
新增跨节能力只改这一个类,实验页也重新变回"只讲自己那件事"。
`SectionEnv` 是纯数据,节号、进度、术语读法都能进单元测试。

## 设计上的几条硬规矩

这几条都是踩过坑之后写进代码注释的,改代码时请一并读:

1. **仿真器永远产生真实的物理延迟,解算器按配置决定改正哪些。**
   电离层、对流层、相对论偏心项在信号里客观存在,不该由仿真器"关掉"。

2. **解不出来的状态必须一路传成 `null`,不能吞成 0.0。**
   0.0 会被 `max/min` 当成一个"误差为零"的真实数据点,直接把结论带偏。
   (曾经真的发生过:一颗星都收不到的场景被渲染成绿色的 "0.0000 m" 并判"达标")
   所以 `ShotResult.errorM` 只喂引擎内部的统计;凡是显示给用户的地方走
   `horizontalError: Double?` 与 `passes()`,判"达标"的规则只有 `passes` 一处。

3. **凡是"算出新状态再写回"的地方,先抽成纯函数再接 UI。**
   (曾经把 `current = current + 1` 写成 `current + 1`,lambda 算完就丢,按钮点了没反应,
   编译通过、40 个测试全绿也没抓到)

4. **测试必须从界面实际调用的那个函数取数,不允许另配一份预算。**
   (曾经测试验的是 0.588 m、屏幕显示的是 6.211 m,两边都在"通过")

5. **星座模型里,轨道面 → ECEF 的旋转顺序是先 rotX(倾角) 再 rotZ(升交点)。**
   反了的话 Ω 会混进近点角,卫星全挤在同一条大圆上,HDOP 直接爆到几百。

6. **标签承诺的量,必须就是代码注入的量。**
   (第 06 节滑块标签写着「卫星间钟差」、提示写着「四条曲线会一起飞出去」,
   代码注入的却是 `receiverClockNs` —— 第 01 节花整节说明会被完整吸收的共模量。
   拖到 0 / 50 / 200 ns,三条曲线一模一样,滑块是个死控件)
   凡是靠一句话约定连接"标签"和"注入字段"的地方,都要有一条测试把两者钉在一起。

7. **跨节的能力走 `SectionEnv`,不要新开一条平行参数。**
   参数多到某个数目时,总会有一条路径漏掉 —— 首页画了开关,节里却读不到,
   于是控件"点了没反应"。收进一个对象就不会漏。
